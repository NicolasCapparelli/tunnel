## Transfers and receipts

A Quanta contains ID, text, creation time as positive integer Unix milliseconds and optional attachments. Text preserves whitespace/Unicode and is at most 64 KiB UTF-8; empty text is valid when files are present. Each attachment carries name, MIME type and exact byte size in its manifest, plus a private URI in local history. Native wire delivery separates metadata from ordered base64 chunks. Up to 32 attachments share a 250 MiB aggregate limit. Names exclude path separators/control characters; received paths are allocated locally from validated IDs and indices, never sender names. Binary fixtures cross-check JavaScript/Rust/JCA encryption. Transfer adds sent/received direction, pending/delivered/failed status and peer display name. UUID-like IDs identify retry attempts for one logical transfer; peer labels are presentation, not security identity.

Send starts pending and becomes delivered after acknowledgment or failed after timeout/disconnect. On restore pending entries become failed. Each device keeps the newest 200 history entries; at most 2,000 received IDs survive history clearing for duplicate suppression. Desktop unpair clears its pairing-related state/seen IDs. Phone unlink removes only that desktop and its selected destination; history and other pairings remain. These are bounded windows, not unlimited deduplication guarantees. Clearing a draft happens only after confirmation if the draft still matches the sent value.

## Pairing and wire

Version-1 Pairing carries local ws endpoint, 32-byte hex key, token, expiry, desktop identity and name. Credentials add phone identity/name. QR expiry is enforced on initial pairing; stored credentials can reconnect after it expires. New pairing permits one phone; unlink rotates keys. Wire union has hello, welcome, text, begin, chunk, end, ack, name, ping and pong. Begin carries the quanta manifest without file data/URIs; chunk carries transfer ID, attachment index, exact byte offset and at most 48 KiB decoded data; end triggers complete-size validation and persistence before ack. Text-only quanta retain the text frame. Name carries a trimmed 1–80 UTF-8 byte display label; it does not change the authenticated device ID. Encrypted frame is lowercase hex: 12-byte nonce followed by authenticated ciphertext/tag. Nonces are random; key material must not enter logs or commits.

## Persistence and preferences

Desktop writes `tunnel.json` in Tauri application data using a temporary file then rename; source intends durable receipt but does not establish full crash/power-loss guarantees. Runtime sender, pending receipts and QR session are memory-only. Phone credentials use the `tunnel-links` registry in SecureStore; legacy `tunnel-link` is migrated on restoration. AsyncStorage keys include theme, history plus seen IDs, draft, device identity, editable device name, auto-copy, tunnel-send-layout (left/right/under) and tunnel-under-control (slider/button). Native Android credentials are AES-GCM encrypted with a Keystore key in app-private preferences; native inbox and seen IDs are committed together before receipt. Pending native inbox holds 200 entries, seen IDs 2,000. UI consumes them oldest-first, preserving the latest clipboard value on resume, then removes each pending entry after UI history persistence. Native inbox text is locally stored without application encryption, as is AsyncStorage history. Restoration validates incoming records, bounds collections and repairs pending status; malformed credentials are removed.

Desktop draft/theme live in WebView localStorage. Theme IDs are mineral/dune/tide; appearance light/dark/system, restored through validated defaults. Phone default auto-copy is true. Android native share settings default to instant text and reviewed image/file shares. A native outbox commits shares before closing its intake activity, retains stable IDs and original desktop identity, and sends pending shares on connection; failures remain retryable in history. The JS adapter persists sent state before consuming completed native outbox entries. Outbox holds at most 200 shares; a full queue rejects additional intake rather than evicting pending shares. Native pending sends survive process restart; UI restoration repairs pending history until native status is remerged. Stored/transferred text remains locally readable outside credential stores; deletion means removing local history/draft or credentials, not a remote backup deletion. No cloud backup service exists in Tunnel.

## Attachment storage and sharing

[Mobile file adapter](../../apps/mobile/src/files.ts) copies picks/shared files to durable document storage before composing; drafts retain metadata under tunnel-attachments. Native [LinkFiles](../../apps/mobile/modules/tunnel-link/android/src/main/java/app/tunnel/link/LinkFiles.kt) writes received/instant-shared bytes under private attachments/ID/index, then persists inbox/outbox metadata. Desktop stores attachments beside tunnel.json and strips bytes from history; retry reconstructs data from locally owned files. Desktop prunes only IDs removed from the previously persisted history after a successful metadata save, avoiding deletion of a concurrently completing receive. Native incoming streams use unique staging directories and become retained attachment directories after complete validation. Windows clipboard file copies use a locally sanitized filename under the transfer directory, removed with its history files. Mobile releases prior history files while preserving retained transfers/drafts and native pending inbox/outbox references. Failed imports/crashes can leave orphan files; this is not a secure erasure guarantee. Mobile composer files removed without history may remain until app data is cleared. All attachment data is readable in private app storage, without additional at-rest encryption.

Selected-text ACTION_PROCESS_TEXT and SEND/SEND_MULTIPLE resolve to [ShareActivity](../../apps/mobile/modules/tunnel-link/android/src/main/java/app/tunnel/link/ShareActivity.kt). Only content-provider file URIs are imported for instant external shares; this prevents external callers naming arbitrary private file paths. Review passes grants/intents to the main activity. Update both devices together for the chunked attachment protocol. Maximum encrypted hex frame is 1,000,000 characters, bounded before decoding. Attachment receipt timeout is 300 seconds (Android starts this after enqueueing the end frame). Send/receive queues are bounded; native files stream from/to disk rather than one whole base64 string. The shared JavaScript fallback assembles at most 5 MiB. Interrupted transfers can be retried with the same ID, but there is no offset resume/progress protocol yet.

Android camera capture copies each accepted JPEG from Expo cache into the existing private `quanta/` draft storage and validates the combined attachment count/size before adding it. A rejected copied photo is deleted. OCR uses the bundled Latin-script ML Kit model through the native module, accepts only canonical file paths inside the app cache, and appends recognized text after a newline while enforcing the combined 64 KiB UTF-8 limit. Empty recognition or overflow leaves the draft unchanged. OCR capture retains its temporary cache photo during crop review and failed-recognition retries. The crop uses normalized upright-image coordinates; the native module validates its finite bounds, decodes with EXIF orientation, caps the decoded image’s longest side at 4096 px, and crops before ML Kit recognition. The default full-image rectangle scans everything. Temporary OCR photos are deleted on review close, successful recognition or Retake; they are not retained as attachments. Regular camera temporary files are deleted after import success/failure. No protocol/schema or automatic-send change. Camera capture requires permission; capture is locked while processing and unmounts the preview in the background. Device behavior remains pending H16.

## Multi-desktop registry and recipient identity

[devices.ts](../../packages/shared/src/devices.ts) owns the bounded eight-desktop credential list and destination validation. Legacy single credentials restore as the first peer even after QR expiry; malformed peers are skipped individually. Adding/re-pairing upserts only its server ID. SecureStore writes are serialized; AsyncStorage `tunnel-destinations` contains explicit selected server IDs, including an intentional empty selection. Selection does not depend on display names or connection status.

Native LinkStore retains encrypted legacy credentials or a `{devices:[Credentials]}` envelope under the existing Keystore-protected preferences key. Native destination IDs live separately; reads/updates are synchronized. Before registry additions/removals, legacy inbox records receive and persist their original server ID. Service snapshots expose per-peer status/name/error and transfer data, never keys. Each PeerSession decrypts/checks identity with its own credentials and drains only matching queued records. Unlink marks only that peer's queued records failed.

Mobile Transfer has optional local `serverId`: destination for sent records, source for received records. Fanout allocates a separate receipt UUID per recipient and preserves the same note/private attachment references. All-recipient success clears an unchanged composer; partial failure retains the draft and independent history statuses. Retry reuses one recipient's ID and original destination; an unlinked destination cannot reroute. Legacy untagged sent records are retryable only when exactly one desktop remains, otherwise require a newly composed explicit send. Native instant intake copies files once then queues per-recipient records; the 200-record queue bound counts recipients. No grouped-transfer schema, offset resume or remote storage is introduced.

## Singularity shared data

The shared store has three Entanglement collections: `singularity_quanta` (raw text and creation time), `singularity_spaces` (user-named groups such as projects), and `singularity_entries` (structured title/body documents tied to a space by a validated reference). [Shared schema and opener](../../packages/shared/src/singularity.ts) configures the Cloudflare adapter and Entanglement realtime mode. Sync metadata, local document storage and remote commits are separate from Tunnel's device-transfer history. The signed Cloudflare Access JWT identifies the owning user; each user maps to an isolated SQLite Durable Object. This version shares across that user's signed-in devices and does not expose spaces to other accounts.

The current schema stores text fields only. Attachments are not implemented. OAuth credentials, account identity, versioned client-registration profile and pending PKCE state/verifier are stored in the platform vault; account-keyed local SQLite adapters persist Entanglement state. The Worker initializes its SQLite tables in the Durable Object constructor. Raw items order by their creation timestamp; server commit revisions order sync, not display chronology.

The client-registration profile records the redirect URI, supported scope list and request version. A mismatch triggers one fresh dynamic registration on sign-in. The owning account and local content remain unchanged until successful callback/account verification.

The Dusk one-field space composer derives an 80-character first-line title while retaining the complete original text in `body`. Shared helpers preserve older separate titles when copying. Moving a raw quantum into a space atomically writes an entry with its existing ID/creation time, deletes the raw item and updates the target space timestamp; no schema or wire-protocol change. Phone entries can also move between spaces.
